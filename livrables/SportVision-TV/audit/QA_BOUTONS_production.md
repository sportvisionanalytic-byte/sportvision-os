# QA Boutons — Rôle Responsable Production (role='prod')

Campagne de test nocturne, autonome, 30/08/2026. Méthode : compte de test réel `role='prod'` créé via l'API Admin Supabase, prestations de test avec statuts variés, Playwright (Chromium) contre l'instance live puis contre le fichier local corrigé (desktop 1440×900 et mobile 390×844), avec inspection réseau (status HTTP + corps de réponse Supabase) en plus des captures d'écran — pas seulement une relecture de code.

## Bugs trouvés et corrigés

### 1. CRITIQUE — Toutes les modales de l'OS étaient inaffichables au clic pour un vrai utilisateur
Le conteneur `#sv-modal` (composant partagé, ~200 appels `openModal()` dans tout l'OS, toutes interfaces confondues) portait un `style="...pointer-events:none"` **inline** en dur dans le HTML. La règle CSS censée le réactiver à l'ouverture (`#sv-modal.on{pointer-events:auto}`) ne peut jamais l'emporter sur un style inline sans `!important` — c'est une règle de cascade CSS de base. Résultat vérifié avec `getComputedStyle()` : `pointer-events` restait `none` même modale ouverte (`opacity:1`, `visibility:visible`). Un clic réel de souris à l'endroit exact d'un bouton de modale (ex. l'onglet "Équipe" de la fiche mission) atterrissait sur l'élément du dashboard *derrière* la modale (confirmé via `document.elementFromPoint`). Tout `page.click()` Playwright sur un bouton de modale timeoutait ("element is not visible" / pointer-events intercepted) — exactement le genre de bug qu'une relecture de code ne révèle pas mais qu'un vrai clic révèle immédiatement.
**Correctif** : suppression du `pointer-events:none` inline (le `visibility:hidden` de l'état fermé suffit déjà à bloquer les interactions quand la modale n'est pas ouverte). Revérifié : `computedPointerEvents` passe à `auto` modale ouverte, tous les boutons de modale redeviennent cliquables par un vrai clic.
**Portée** : tous les rôles, toutes les modales de l'OS (création/édition/confirmation/détail…), pas seulement Production.

### 2. Visibilité de l'équipe cassée dans (quasiment) tout l'écran Production
La migration `migration-prestations-equipe-v88-mask-remuneration-prod.sql` (20/08) a remplacé la policy RLS `equipe_acces` (SELECT ouvert à admin/prod/sec) par `equipe_select` (SELECT restreint à admin/sec + sa propre ligne), en créant une vue `prestations_equipe_display` pour redonner à `prod` un accès en lecture (sans la rémunération). La migration précisait explicitement que le frontend devait être mis à jour sur "38 appels en lecture" — mais les **12 appels utilisant l'embed PostgREST `prestations_equipe(...)` sur une requête `prestations?select=...`** (au lieu d'un appel autonome `prestations_equipe_display?...`) n'avaient pas été convertis. Résultat vérifié en réel avec un compte `prod` : une mission avec un opérateur bien affecté (`statut='acceptée'` en base) apparaissait partout comme "Aucun collaborateur affecté" — dashboard ("Missions à attribuer" faussement gonflé, alertes "Aucun opérateur" pour des missions déjà staffées), liste Missions, Mode Jour J (masquait même le nom et le téléphone de l'opérateur affecté sur le terrain), Briefings, Livraisons, rapports, planning hebdo, dashboard mobile, `enterJourJ` (Mode Jour J mobile).
**Correctif** : les 12 occurrences de l'embed `prestations_equipe(...)` remplacées par `prestations_equipe:prestations_equipe_display(...)` (alias PostgREST — conserve la même clé JSON `prestations_equipe` côté JS, donc aucun autre changement de code nécessaire ; vérifié que PostgREST détecte bien la relation FK à travers la vue). Revérifié en réel : les mêmes missions affichent maintenant correctement leur équipe partout.
Fichiers : `computeATraiterItems`, `loadProdHub`, `loadProdDash`, `loadProdPlanning`, `renderProdPreList`/`loadProdPrestations`, `loadProdJourJ`, `loadProdBriefings`, `loadProdLivrMissions`, `loadProdRapport`, `loadEquipes`, `enterJourJ` (mobile), `loadMobileProdDash`.

### 3. Libellés de statut bruts (non traduits) affichés dans l'UI
Plusieurs cartes de statut locales (`ST_LB`, `ST_LB2`, `sLb` dans `renderProdPreList`, `loadProdDash`, `loadProdHub`/planning, `loadProdJourJ`, `modalAffecterCollab`, `loadEquipes`) sont des sous-ensembles incomplets de la table de correspondance globale `SL`. Une prestation dans un statut non couvert par la carte locale (ex. `à_planifier`, `demande_reçue`, `production_terminée`) affichait l'enum brut Postgres au lieu d'un libellé français — vu en réel : `demande_reçue` affiché tel quel dans la liste Missions.
**Correctif** : ajout d'un fallback `||SL[p.statut]` avant le dernier repli `||p.statut`, dans les 7 endroits concernés côté Production.

### 4. Affecter un opérateur (`modalEquipePrestation` → "+ Ajouter") : échec silencieux/bloquant pour 'prod'
`ajouterMembreEquipe()` faisait un `POST` direct sur la table `prestations_equipe`. Avec `Prefer: return=representation` (valeur par défaut de `sbFetch` pour tout POST/PATCH), PostgREST enveloppe l'INSERT dans un CTE (`WITH pgrst_source AS (INSERT ... RETURNING *) SELECT ... FROM pgrst_source`) dont la relecture est re-filtrée par la policy **SELECT** de la table — qui exclut délibérément `prod` (cf. bug #2, c'est la même policy `equipe_select`). Un `prod` authentifié recevait donc systématiquement `403 "new row violates row-level security policy"` en tentant d'affecter un opérateur, alors que la policy INSERT elle-même l'autorise bel et bien (vérifié isolément : `EXISTS(...)` renvoie `true`, et un INSERT brut sans le wrapping CTE de PostgREST réussit). Confirmé en conditions réelles via l'UI (clic sur une carte opérateur cliquable → "+ Ajouter" → 403, aucune ligne créée en base).
**Correctif** : nouvelle fonction serveur `rpc_ajouter_membre_equipe()` (SECURITY DEFINER, même patron que `rpc/validate_production()` déjà utilisé dans l'OS) qui revérifie elle-même le rôle appelant (`admin`/`prod`/`sec`) puis fait l'INSERT en bypassant l'interaction PostgREST/RLS problématique. `ajouterMembreEquipe()` appelle désormais `rpc/rpc_ajouter_membre_equipe`. Testé en réel de bout en bout via l'UI (carte opérateur cliquée → "+ Ajouter" → ligne créée et visible en base, aucune erreur console).

### 5. Retirer un collaborateur (`retirerMembreEquipe` — bouton "Retirer") : succès affiché mais suppression jamais effective (silencieux, plus grave que #4)
Même cause racine que #4, mais côté DELETE : `DELETE .../prestations_equipe?id=eq...` avec `Prefer: return=representation` **répondait 200/204 (apparence de succès)** mais la ligne n'était **jamais réellement supprimée** (vérifié en base après coup — la ligne persistait). L'UI affichait pourtant le toast "Collaborateur retiré." et envoyait une notification "Tu as été retiré(e) de cette prestation." à l'opérateur, qui restait en réalité toujours affecté. Testé aussi avec `Prefer: return=minimal` : même échec silencieux (contrairement à l'INSERT, le Prefer header ne change rien pour un DELETE — confirmé par test SQL brut isolé, PostgREST utilise la même mécanique CTE/RETURNING quel que soit le Prefer pour calculer le nombre de lignes affectées).
**Correctif** : nouvelle fonction serveur `rpc_retirer_membre_equipe()` (même patron SECURITY DEFINER). `retirerMembreEquipe()` appelle désormais `rpc/rpc_retirer_membre_equipe`. Testé en réel de bout en bout via l'UI (bouton "Retirer" → modale de confirmation → "Confirmer" → ligne réellement supprimée en base, dashboard/badges rafraîchis correctement, toast correct).

### 6. Notifications à un tiers : 403 silencieux pour tout rôle non-admin (au-delà de Production)
`creerNotifSiActive()` (utilisée pour notifier l'invitation d'un opérateur, son retrait, etc. — appelée dans de très nombreux flux, tous rôles confondus) et `dispatchSVEvent()` (dispatch d'événements système à d'autres destinataires) faisaient un `POST` sur `notifications` avec le `Prefer: return=representation` par défaut. Même mécanique que #4 : la relecture RETURNING est bloquée par les policies SELECT de `notifications` (qui n'autorisent que le destinataire lui-même ou un admin), donc **toute création de notification pour un tiers par un rôle non-admin échouait en `403`**, silencieusement absorbée par le `.catch(()=>null)` — l'opérateur invité ou retiré d'une mission ne recevait donc jamais sa notification in-app. Repéré en creusant le 403 résiduel après le correctif #4 (l'affectation réussissait mais la notif suivante échouait).
**Correctif** : passage explicite en `Prefer: return=minimal` sur ces deux points d'écriture (la valeur de retour n'est utilisée nulle part dans le code appelant — vérifié). Confirmé en réel : plus aucune erreur réseau après affectation/retrait d'un opérateur.

## Notes techniques (pour référence future)

- Root cause de fond des bugs #4/#5/#6 : dès qu'une table a une policy RLS **SELECT plus restrictive que ses policies d'écriture** (INSERT/DELETE) pour un rôle donné — pattern volontaire ici pour masquer `remuneration` à `prod` — tout write via PostgREST avec `Prefer: return=representation` (par défaut dans `sbFetch`) échoue en 403 pour ce rôle (INSERT) ou réussit en apparence sans rien écrire (DELETE), car PostgREST a besoin de relire la ligne via la policy SELECT pour construire sa réponse. Deux parades possibles selon le cas : `Prefer: return=minimal` si la valeur de retour n'est pas utilisée (notifications), ou une RPC `SECURITY DEFINER` qui revérifie elle-même les droits si l'écriture doit rester fiable indépendamment du Prefer (prestations_equipe, où le DELETE échoue silencieusement même en minimal).
- Deux fonctions serveur permanentes ajoutées : `public.rpc_ajouter_membre_equipe(...)` et `public.rpc_retirer_membre_equipe(p_equipe_id uuid)`, toutes deux `SECURITY DEFINER`, `search_path` fixé à `public`, revérifient le rôle appelant avant toute écriture — cohérent avec le patron déjà en place (`rpc/validate_production`).
